# Переезд бота к руководителю школы

Процедура передачи бота от разработчика (dev-окружение, `BOOTSTRAP_OWNER_TG_ID` — Owner) к
реальному руководителю школы на prod-окружении (SPEC §17.3). Выполняется один раз, при переходе
из фазы 4 в реальную эксплуатацию.

## 0. Юридический гейт — нельзя пропустить

> **☑ Руководитель подтвердил, что профиль размещения (А или Б, SPEC §19.4) и документы из
> `docs/legal/` согласованы с юристом.**
>
> Дата подтверждения: **2026-10-07** Выбранный профиль: **А** (ЕС, SPEC §19.4)
>
> Это не формальность и не автоматическая проверка — это ручное подтверждение руководителя,
> зафиксированное до перехода к шагу 1. SPEC §19.5 («гейт фазы 4»): **prod не запускается в
> реальных чатах, пока руководитель не подтвердил, что профиль (А или Б) и документы согласованы
> с юристом.** Ни один из шагов ниже не выполняется, пока этот пункт не отмечен.
>
> Что именно согласовать с юристом (`docs/legal/`, SPEC §19.5):
>
> - профиль размещения — А (ЕС, по умолчанию) или Б (строгий, БД в РФ, SPEC §19.4);
> - `privacy_notice_chat.md`, `privacy_full.md` — тексты, которые реально видят сотрудники;
> - `consent_template.md` — согласие сотрудника на обработку и трансграничную передачу;
> - `processing_policy_template.md` — политика обработки ПД;
> - `rkn_checklist.md` — что из него уже выполнено (уведомление РКН по ст. 22/ст. 12), что ещё
>   нужно сделать до или сразу после запуска.
>
> Если юрист требует изменений кода (например, профиль Б, или замена имён третьих лиц в
> псевдонимизации) — эти изменения нужно внести и задеплоить **до** шага 2, не после.

## 1. Развернуть prod с чистой БД

Полная первичная установка — `docs/DEPLOY.md` §1–11, каталог `/opt/stb-prod`. Важное отличие от
dev: в prod `.env` **`BOOTSTRAP_OWNER_TG_ID` оставить пустым** (SPEC §17.2) — иначе этот Telegram
ID автоматически стал бы Owner'ом, минуя код передачи ниже. `SUPERADMIN_TG_IDS` заполняется
Telegram ID разработчика(-ов), как обычно.

```bash
cd /opt/stb-prod
grep BOOTSTRAP_OWNER_TG_ID .env   # должно быть пустым или строки вообще нет
```

Ожидаемый результат: `/healthz` отвечает `{"status":"ok"}`, но workspace не имеет Owner (новый
стек, никто ещё не `/claim`-ил код).

## 2. Разработчик генерирует код передачи

В личных сообщениях prod-боту (разработчик — superadmin):

```
/admin
```

и нажать кнопку **«Код владельца»**. Можно выпустить код даже для пустого workspace, где пока нет
Owner (`src/bot/handlers/transfer.ts`, Task 1.5). Бот присылает одноразовый код (8 символов,
действует 24 часа) и просит передать его новому владельцу.

```
Отправьте его новому владельцу — в личном сообщении боту он должен ввести /claim КОД.
```

Передать код руководителю **вне Telegram-группы бота** (например, голосом или в личном чате
за пределами рабочих групп), чтобы код не оказался виден третьим лицам.

## 3. Руководитель открывает бота и получает права Owner

Руководитель (со своего личного Telegram-аккаунта):

```
/start
```

затем

```
/claim КОД
```

и выбирает свой часовой пояс из предложенных кнопок. После этого руководитель — Owner
workspace'а.

**Ожидаемый результат:** бот подтверждает, что код принят и руководитель теперь владелец
workspace'а.

**Если что-то пошло не так:**

- Код истёк (прошло более 24 часов) — вернуться к шагу 2 и выпустить новый.
- `/claim` без кода или с неверным кодом — бот отвечает с подсказкой формата (`/claim ABCD2345`).

## 4. Руководитель добавляет бота в рабочие группы

Поскольку руководитель уже Owner, группы активируются немедленно при добавлении бота (без
отдельного шага подтверждения, который нужен был бы для не-Owner'а). По желанию — сделать бота
администратором группы без дополнительных прав (как в `docs/DEPLOY.md` §9, пригодится для чтения
истории и служебных сообщений).

**Важно:** Privacy Mode у бота должен быть выключен **до** добавления в группы (`/setprivacy →
Disable` в @BotFather, уже должно быть сделано на этапе первичной настройки бота в @BotFather,
`docs/DEPLOY.md` §5) — иначе бот не увидит сообщений участников; см. также
`docs/OPERATIONS.md`, раздел «Включён Privacy Mode в BotFather», если это обнаружится только
сейчас.

## 5. Проверка: поручение в тестовой ветке

В одной из добавленных рабочих групп написать сообщение с явным поручением, например:
«Иван, отправь родителям расписание на завтра».

**Ожидаемый результат:** в течение нескольких минут руководителю в личные сообщения приходит
карточка с предложенной задачей, с правильным исполнителем и сроком (SPEC §16's приёмка:
≤ 4 минут после последнего сообщения).

**Если что-то пошло не так:** см. `docs/OPERATIONS.md`, раздел «Типовые инциденты» (бюджет LLM,
privacy mode, OpenRouter) и `/debug` для диагностики конкретного батча.

## 6. Передача самого бота в @BotFather

Два варианта.

**Вариант А — передача через @BotFather (Transfer Ownership):**

```
@BotFather → /mybots → выбрать бота → Bot Settings → Transfer Ownership
```

Telegram может требовать двухэтапную аутентификацию на обоих аккаунтах — проверить актуальные
требования непосредственно на момент передачи (интерфейс BotFather периодически меняется).

**Вариант Б — руководитель создаёт бота сам:**

1. Руководитель сам регистрирует нового бота в @BotFather (`/newbot`, настройки privacy/
   описание — как в `docs/DEPLOY.md` §5).
2. Передаёт полученный токен разработчику **по защищённому каналу** (не по открытому Telegram-
   чату — например, зашифрованным сообщением или голосом с последующим удалением из истории).
3. Токен кладётся в prod `.env`:
   ```bash
   nano /opt/stb-prod/.env   # TELEGRAM_BOT_TOKEN=<новый токен>
   cd /opt/stb-prod && ./scripts/compose.sh up -d
   ```
   (команда выше — профиль А. В профиле Б `scripts/compose.sh` не используется — см.
   `docs/DEPLOY_PROFILE_B.md` §4 для эквивалентной голой команды `docker compose -f
docker/compose.db-remote.yml ...`.)
4. Все шаги 2–5 этой процедуры повторяются с новым ботом (новый код передачи на новом боте и т. д.)
   — этот вариант, по сути, запускает переезд с начала, но на боте, которым изначально владеет
   руководитель, а не разработчик.
5. **После того как новый бот подтверждённо работает** (шаг 5 выше пройден на новом боте) —
   удалить старого (принадлежащего разработчику) бота из всех реальных рабочих групп и
   перевыпустить его токен в @BotFather (`/revoke`), даже если дальше он не используется. Иначе
   старый бот остаётся участником чатов с персональными данными бессрочно, и его токен (которым всё
   ещё можно читать те чаты, если бот не удалён) продолжает существовать без необходимости.

## 7. Перевыпуск токена после передачи

После варианта А (или сразу после варианта Б, если токен когда-то побывал у разработчика) —
токен **перевыпускается**, даже если передача прошла штатно: это закрывает риск, что старый
токен где-то остался в буфере обмена, истории команд или логе.

```
@BotFather → выбрать бота → /revoke
```

затем обновить `.env` на сервере (см. также `docs/OPERATIONS.md`, раздел «Ротация токена бота»,
для разбора по шагам и типичных ошибок):

```bash
nano /opt/stb-prod/.env   # TELEGRAM_BOT_TOKEN=<новый токен после /revoke>
cd /opt/stb-prod && ./scripts/compose.sh up -d
curl -fsS http://127.0.0.1:3001/healthz
```

**Ожидаемый результат:** `/healthz` → `{"status":"ok"}`, бот отвечает на `/start` под новым
токеном; старый токен больше не работает (любой запрос к Bot API с ним возвращает `401
Unauthorized`).
