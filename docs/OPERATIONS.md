# OPERATIONS — эксплуатация school-task-bot

Справочник для эксплуатации прод/dev-стека: что делать по расписанию, что делать при сбое, где
лежат ключи. Для первичной установки сервера (покупка VPS, Docker, `.env`, первый деплой) — см.
`docs/DEPLOY.md`.

Разделы этого файла — независимые `##`-блоки; при добавлении новых (логи, `/admin`, диагностика,
инциденты, ротация токенов — задача 4.3) просто дописывайте новый `##` после последнего, ничего в
существующих разделах не предполагает, что они здесь единственные.

## Бэкапы

### Что уже есть

- `scripts/backup.sh` — ежедневный дамп `pg_dump` → `gzip` → шифрование `age` (публичным ключом
  `BACKUP_AGE_RECIPIENT` из `.env`), хранит 14 последних файлов на окружение в `backups/` и
  отправляет зашифрованный файл superadmin'у в Telegram (документом), если он ≤ 50 МБ.
- `scripts/restore.sh <file.age> <identity-file>` — восстановление: останавливает `app`,
  пересоздаёт БД, накатывает дамп, поднимает `app` обратно на том же теге (`.deploy/current_tag`,
  decision D38) и ждёт `/healthz`.
- **Оповещение superadmin о сбое уже реализовано и не требует доработки.** `scripts/backup.sh`
  устанавливает перехват ошибок (`trap ... ERR`, `scripts/backup.sh:69`) и функцию `fail()`
  (`scripts/backup.sh:61-67`) ещё до того, как прочитана хоть одна переменная из `.env` — так что
  любой сбой (нечитаемый `.env`, отсутствующая переменная, упавший `pg_dump`, пустой файл дампа)
  проходит через `fail()`, которая зовёт `alert_superadmin()` (`scripts/backup.sh:49-57`) —
  `sendMessage` через Bot API на первый ID из `SUPERADMIN_TG_IDS`. Единственный случай, когда
  оповестить некого, — если в `.env` нет самих `TELEGRAM_BOT_TOKEN`/`SUPERADMIN_TG_IDS`; тогда
  сообщение уйдёт только в stderr/лог cron (см. `docs/DEPLOY.md` §10, «если что-то пошло не так»).
- Раунд-трип бэкапа/восстановления проверен скриптом `scripts/test-backup-restore.sh` (полностью в
  Docker, на синтетической фикстуре, без реального сервера и без реальных вызовов Telegram API —
  см. его собственный заголовочный комментарий). Он также проверяет, что сравнение `count(*)`
  действительно ловит неполное восстановление (намеренно портит дамп перед вторым восстановлением
  и требует, чтобы счётчики не совпали).

Установка `age`, генерация ключевой пары и формат `.env` — см. `docs/DEPLOY.md` §10; здесь не
дублируется, см. там.

### Ротация ключа и бэкапов

- **Ключ шифрования (`age`) не ротируется автоматически.** Он создаётся один раз на окружение
  (dev/prod — разные ключи) при установке сервера (`docs/DEPLOY.md` §10). Планово менять его не
  требуется: компрометация приватного ключа не даёт доступа ни к чему, кроме уже сделанных
  бэкапов (не к живой БД), а публичный ключ (`BACKUP_AGE_RECIPIENT`) не секретен.
  - Если приватный ключ всё же скомпрометирован (утёк офлайн-носитель/менеджер паролей):
    1. Сгенерировать новую пару: `age-keygen -o stb-<env>-backup-key-v2.txt`.
    2. Обновить `.env` на сервере: `BACKUP_AGE_RECIPIENT=age1...` (новый публичный ключ).
    3. Новый приватный ключ — туда же, где лежал старый (см. «Где лежит приватный ключ» ниже);
       старый приватный ключ после этого хранить не нужно, но старые бэкапы, зашифрованные им,
       остаются восстановимыми только им — не уничтожать старый ключ, пока эти бэкапы ещё нужны
       (14-дневное окно хранения, см. ниже).
- **Файлы бэкапов** ротируются автоматически: `scripts/backup.sh` хранит 14 самых новых файлов на
  окружение (`backups/stb-<env>-*.sql.gz.age`) и удаляет более старые при каждом запуске
  (`scripts/backup.sh:121-129`, `KEEP_COUNT=14`). Это окно — ~2 недели при ежедневном cron (SPEC
  §27.10). Файлы ≤ 50 МБ дополнительно уходят в Telegram superadmin'у (саморезервная копия вне
  сервера на каждый день); файлы больше 50 МБ остаются только на сервере — забирать их `scp`
  вручную, если нужна копия вне сервера (см. `docs/DEPLOY.md` §10, «если что-то пошло не так»).

### Где хранится приватный ключ (вне сервера)

Приватный `age`-ключ **никогда не остаётся на сервере** (`docs/DEPLOY.md` §10: сразу после
генерации — `scp` себе и `shred -u` на сервере). Хранить офлайн/в менеджере паролей, отдельно на
каждое окружение:

- dev: `~/secure/stb-dev-backup-key.txt` (или аналогичный путь в менеджере паролей руководителя/
  оператора).
- prod: `~/secure/stb-prod-backup-key.txt` — отдельный ключ от dev, не путать: восстановление с
  неверным ключом падает с `age: error: no identity matched any of the recipients` (безопасно,
  БД к этому моменту ещё не тронута — `restore.sh` расшифровывает дамп до `DROP DATABASE`).

Публичный ключ (`BACKUP_AGE_RECIPIENT`) секретным не является и живёт в `.env` на сервере — это
нормально, он только шифрует, восстановить дамп им нельзя.

### Cron на проде

```
0 3 * * * /opt/stb-prod/scripts/backup.sh >> /var/log/stb-backup.log 2>&1
```

03:00 UTC, ежедневно (SPEC §27.10), по аналогии с dev-строкой из `docs/DEPLOY.md` §10
(`/opt/stb-dev/scripts/backup.sh >> /var/log/stb-dev-backup.log 2>&1`). Установка:

```bash
crontab -e   # пользователь deploy на прод-сервере
```

добавить строку выше. Как и для dev, `scripts/backup.sh` сам находит и парсит `.env` из своего
каталога — в crontab ничего дополнительно экспортировать не нужно; про минимальный `PATH` у cron
(нужны `docker`/`age` в `PATH`) — см. `docs/DEPLOY.md` §10.

**Установка этой строки в реальный crontab прод-сервера — ручной шаг (👤), выполняется оператором
на самом сервере через `ssh`.** Она не выполнена в рамках этой задачи и не может быть выполнена
агентом: агент не подключается к реальному серверу и не трогает реальный crontab. После установки
проверить первый прогон вручную (`./scripts/backup.sh` из `/opt/stb-prod`) и убедиться, что
superadmin получил документ в Telegram, прежде чем полагаться на cron.

### Пошаговое восстановление на чистом сервере

Сценарий: сервер потерян/переустановлен, нужно поднять стек с нуля и восстановить данные из
последнего бэкапа.

1. Выполнить первичную установку сервера с нуля: покупка VPS, Docker, получение кода, `.env`,
   первый деплой — **целиком по `docs/DEPLOY.md` §1–8**, вплоть до первого успешного
   `./scripts/compose.sh up -d` и `/healthz`. На этом шаге БД будет пустой (новый volume) — это
   ожидаемо, дальше она будет пересоздана восстановлением.
2. Установить `age` и завести `.env`-запись `BACKUP_AGE_RECIPIENT` — см. `docs/DEPLOY.md` §10.
   **Важно:** `BACKUP_AGE_RECIPIENT` должен быть ТЕМ ЖЕ публичным ключом, которым шифровался
   восстанавливаемый бэкап (т. е. тем, что был на старом сервере) — если ключ менялся (см.
   «Ротация» выше), для старых бэкапов нужен старый публичный+приватный ключ, не новый.
3. Скопировать на сервер (`scp`) сам файл бэкапа и соответствующий приватный `age`-ключ (который
   хранится вне сервера, см. выше):
   ```bash
   scp ~/secure/stb-prod-backup-key.txt deploy@<IP>:/tmp/
   scp <последний_известный_бэкап>.sql.gz.age deploy@<IP>:/opt/stb-prod/backups/
   ```
   (последний бэкап до потери сервера обычно также лежит в личке superadmin'а в Telegram, если он
   был ≤ 50 МБ — можно скачать его оттуда, если локальной копии нет.)
4. Убедиться, что записан тег текущей версии (`restore.sh` перезапускает `app` именно на нём,
   decision D38): `cat .deploy/current_tag`. Если файла нет (новый сервер) — он уже должен быть
   записан первым деплоем на шаге 1; если всё же нет, записать вручную тем тегом, что реально
   развёрнут (`docker ps`, колонка `IMAGE`): `echo v0.1.0-rc.1 > .deploy/current_tag`.
5. Запустить восстановление:
   ```bash
   cd /opt/stb-prod
   ./scripts/restore.sh backups/stb-prod-<TIMESTAMP>.sql.gz.age /tmp/stb-prod-backup-key.txt
   ```
   Скрипт покажет версию, на которой перезапустит `app`, попросит подтверждение
   (`Type 'yes' to continue:`), затем пересоздаст БД, накатит дамп и подождёт `/healthz` (до 90
   секунд). Ожидаемый финал: `Restore complete; app is healthy.`
6. Удалить временный приватный ключ с сервера (он не должен там оставаться):
   ```bash
   shred -u /tmp/stb-prod-backup-key.txt
   ```
7. Проверить работоспособность вручную: `/start` в личке руководителя, одна из рабочих групп
   отвечает на `/task` — то есть, что данные (участники, группы, задачи) действительно на месте,
   а не просто что `/healthz` зелёный.

Если что-то пошло не так на шаге 5 — см. «Если что-то пошло не так» в `docs/DEPLOY.md` §10
(неверный ключ, не записан тег, и т.д.); та же механика восстановления используется и для прода.
