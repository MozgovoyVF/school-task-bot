# OPERATIONS — эксплуатация school-task-bot

Справочник для эксплуатации прод/dev-стека: что делать по расписанию, что делать при сбое, где
лежат ключи. Для первичной установки сервера (покупка VPS, Docker, `.env`, первый деплой) — см.
`docs/DEPLOY.md`.

Разделы этого файла — независимые `##`-блоки (логи, `/admin`, `/debug`, диск, обновление и откат,
типовые инциденты и т. д.); при добавлении новых разделов в будущих фазах просто дописывайте новый
`##` после последнего — ничего в существующих разделах не предполагает, что они здесь единственные.

## Бэкапы

### Что уже есть

- `scripts/backup.sh` — ежедневный дамп `pg_dump` → `gzip` → шифрование `age` (публичным ключом
  `BACKUP_AGE_RECIPIENT` из `.env`), хранит 14 последних файлов на окружение в `backups/` и
  отправляет зашифрованный файл superadmin'у в Telegram (документом), если он ≤ 50 МБ.
- `scripts/restore.sh <file.age> <identity-file>` — восстановление: останавливает `app`,
  пересоздаёт БД, накатывает дамп, поднимает `app` обратно на том же теге (`.deploy/current_tag`,
  decision D38) и ждёт `/healthz`.
- **Оповещение superadmin о сбое уже реализовано и не требует доработки.** `scripts/backup.sh`
  устанавливает перехват ошибок (`trap ... ERR`, `scripts/backup.sh:69`) и функцию `fail()`
  (`scripts/backup.sh:61-67`) ещё до того, как прочитана хоть одна переменная из `.env` — так что
  любой сбой (нечитаемый `.env`, отсутствующая переменная, упавший `pg_dump`, пустой файл дампа)
  проходит через `fail()`, которая зовёт `alert_superadmin()` (`scripts/backup.sh:49-57`) —
  `sendMessage` через Bot API на первый ID из `SUPERADMIN_TG_IDS`. Единственный случай, когда
  оповестить некого, — если в `.env` нет самих `TELEGRAM_BOT_TOKEN`/`SUPERADMIN_TG_IDS`; тогда
  сообщение уйдёт только в stderr/лог cron (см. `docs/DEPLOY.md` §10, «если что-то пошло не так»).
- Раунд-трип бэкапа/восстановления проверен скриптом `scripts/test-backup-restore.sh` (полностью в
  Docker, на синтетической фикстуре, без реального сервера и без реальных вызовов Telegram API —
  см. его собственный заголовочный комментарий). Он также проверяет, что сравнение `count(*)`
  действительно ловит неполное восстановление (намеренно портит дамп перед вторым восстановлением
  и требует, чтобы счётчики не совпали).

Установка `age`, генерация ключевой пары и формат `.env` — см. `docs/DEPLOY.md` §10; здесь не
дублируется, см. там.

### Ротация ключа и бэкапов

- **Ключ шифрования (`age`) не ротируется автоматически.** Он создаётся один раз на окружение
  (dev/prod — разные ключи) при установке сервера (`docs/DEPLOY.md` §10). Планово менять его не
  требуется: компрометация приватного ключа не даёт доступа ни к чему, кроме уже сделанных
  бэкапов (не к живой БД), а публичный ключ (`BACKUP_AGE_RECIPIENT`) не секретен.
  - Если приватный ключ всё же скомпрометирован (утёк офлайн-носитель/менеджер паролей):
    1. Сгенерировать новую пару: `age-keygen -o stb-<env>-backup-key-v2.txt`.
    2. Обновить `.env` на сервере: `BACKUP_AGE_RECIPIENT=age1...` (новый публичный ключ).
    3. Новый приватный ключ — туда же, где лежал старый (см. «Где лежит приватный ключ» ниже);
       старый приватный ключ после этого хранить не нужно, но старые бэкапы, зашифрованные им,
       остаются восстановимыми только им — не уничтожать старый ключ, пока эти бэкапы ещё нужны
       (14-дневное окно хранения, см. ниже).
- **Файлы бэкапов** ротируются автоматически: `scripts/backup.sh` хранит 14 самых новых файлов на
  окружение (`backups/stb-<env>-*.sql.gz.age`) и удаляет более старые при каждом запуске
  (`scripts/backup.sh:121-129`, `KEEP_COUNT=14`). Это окно — ~2 недели при ежедневном cron (SPEC
  §27.10). Файлы ≤ 50 МБ дополнительно уходят в Telegram superadmin'у (саморезервная копия вне
  сервера на каждый день); файлы больше 50 МБ остаются только на сервере — забирать их `scp`
  вручную, если нужна копия вне сервера (см. `docs/DEPLOY.md` §10, «если что-то пошло не так»).

### Где хранится приватный ключ (вне сервера)

Приватный `age`-ключ **никогда не остаётся на сервере** (`docs/DEPLOY.md` §10: сразу после
генерации — `scp` себе и `shred -u` на сервере). Хранить офлайн/в менеджере паролей, отдельно на
каждое окружение:

- dev: `~/secure/stb-dev-backup-key.txt` (или аналогичный путь в менеджере паролей руководителя/
  оператора).
- prod: `~/secure/stb-prod-backup-key.txt` — отдельный ключ от dev, не путать: восстановление с
  неверным ключом падает с `age: error: no identity matched any of the recipients` (безопасно —
  `restore.sh` расшифровывает и проверяет дамп во временный файл ПЕРВЫМ делом, до запроса
  подтверждения и до `DROP DATABASE`/`CREATE DATABASE`; при ошибке расшифровки или пустом
  результате скрипт останавливается сразу, БД к этому моменту вообще не трогается).

Публичный ключ (`BACKUP_AGE_RECIPIENT`) секретным не является и живёт в `.env` на сервере — это
нормально, он только шифрует, восстановить дамп им нельзя.

### Cron на проде

```
0 3 * * * /opt/stb-prod/scripts/backup.sh >> /var/log/stb-backup.log 2>&1
```

03:00 UTC, ежедневно (SPEC §27.10), по аналогии с dev-строкой из `docs/DEPLOY.md` §10
(`/opt/stb-dev/scripts/backup.sh >> /var/log/stb-dev-backup.log 2>&1`). Установка:

**Сначала — одноразово создать лог-файл с правами на запись для `deploy`** (без этого шага
строка ниже сломается ещё на самом `>>`-редиректе, до запуска `backup.sh`: обычный пользователь
`deploy` не может писать в `/var/log` напрямую — тогда ни бэкапа, ни оповещения не будет, и это
не будет видно, так как сам cron не пришлёт ошибку никуда):

```bash
sudo install -o deploy -g deploy -m 0644 /dev/null /var/log/stb-backup.log
```

(группа `deploy` — замените, если на сервере пользователь `deploy` состоит в другой основной
группе.) Затем:

```bash
crontab -e   # пользователь deploy на прод-сервере
```

добавить строку выше. Как и для dev, `scripts/backup.sh` сам находит и парсит `.env` из своего
каталога — в crontab ничего дополнительно экспортировать не нужно; про минимальный `PATH` у cron
(нужны `docker`/`age` в `PATH`) — см. `docs/DEPLOY.md` §10.

**Установка этой строки в реальный crontab прод-сервера — ручной шаг (👤), выполняется оператором
на самом сервере через `ssh`.** Она не выполнена в рамках этой задачи и не может быть выполнена
агентом: агент не подключается к реальному серверу и не трогает реальный crontab. После установки
проверить первый прогон вручную (`./scripts/backup.sh` из `/opt/stb-prod`) и убедиться, что
superadmin получил документ в Telegram, прежде чем полагаться на cron.

### Пошаговое восстановление на чистом сервере

Сценарий: сервер потерян/переустановлен, нужно поднять стек с нуля и восстановить данные из
последнего бэкапа.

1. Выполнить первичную установку сервера с нуля: покупка VPS, Docker, получение кода, `.env`,
   первый деплой — **целиком по `docs/DEPLOY.md` §1–8**, вплоть до первого успешного
   `./scripts/compose.sh up -d` и `/healthz`. На этом шаге БД будет пустой (новый volume) — это
   ожидаемо, дальше она будет пересоздана восстановлением.
2. Установить `age` и завести `.env`-запись `BACKUP_AGE_RECIPIENT` — см. `docs/DEPLOY.md` §10.
   **Важно:** `BACKUP_AGE_RECIPIENT` должен быть ТЕМ ЖЕ публичным ключом, которым шифровался
   восстанавливаемый бэкап (т. е. тем, что был на старом сервере) — если ключ менялся (см.
   «Ротация» выше), для старых бэкапов нужен старый публичный+приватный ключ, не новый.
3. Скопировать на сервер (`scp`) сам файл бэкапа и соответствующий приватный `age`-ключ (который
   хранится вне сервера, см. выше):
   ```bash
   scp ~/secure/stb-prod-backup-key.txt deploy@<IP>:/tmp/
   scp <последний_известный_бэкап>.sql.gz.age deploy@<IP>:/opt/stb-prod/backups/
   ```
   (последний бэкап до потери сервера обычно также лежит в личке superadmin'а в Telegram, если он
   был ≤ 50 МБ — можно скачать его оттуда, если локальной копии нет.)
4. Убедиться, что записан тег текущей версии (`restore.sh` перезапускает `app` именно на нём,
   decision D38): `cat .deploy/current_tag`. Если файла нет (новый сервер) — он уже должен быть
   записан первым деплоем на шаге 1; если всё же нет, записать вручную тем тегом, что реально
   развёрнут (`docker ps`, колонка `IMAGE`): `echo v0.1.0-rc.1 > .deploy/current_tag`.
5. Запустить восстановление:
   ```bash
   cd /opt/stb-prod
   ./scripts/restore.sh backups/stb-prod-<TIMESTAMP>.sql.gz.age /tmp/stb-prod-backup-key.txt
   ```
   Скрипт покажет версию, на которой перезапустит `app`, попросит подтверждение
   (`Type 'yes' to continue:`), затем пересоздаст БД, накатит дамп и подождёт `/healthz` (до 90
   секунд). Ожидаемый финал: `Restore complete; app is healthy.`
6. Удалить временный приватный ключ с сервера (он не должен там оставаться):
   ```bash
   shred -u /tmp/stb-prod-backup-key.txt
   ```
7. Проверить работоспособность вручную: `/start` в личке руководителя, одна из рабочих групп
   отвечает на `/task` — то есть, что данные (участники, группы, задачи) действительно на месте,
   а не просто что `/healthz` зелёный.

Если что-то пошло не так на шаге 5 — см. «Если что-то пошло не так» в `docs/DEPLOY.md` §10
(неверный ключ, не записан тег, и т.д.); та же механика восстановления используется и для прода.

## Логи

```bash
cd /opt/stb-prod
./scripts/compose.sh logs -f app     # приложение (pino JSON, одна строка — одно событие)
./scripts/compose.sh logs -f db      # Postgres (только профиль А — см. ниже)
```

Обе команды предполагают **профиль А** (`docker/compose.yml`, Postgres в том же стеке,
`docs/DEPLOY.md`). В профиле Б (`docs/DEPLOY_PROFILE_B.md`) `scripts/compose.sh` не используется
вовсе (жёстко привязан к `docker/compose.yml`, который там не задействован) — на EU-сервере логи
приложения смотрятся голой командой `docker compose -f docker/compose.db-remote.yml --env-file
.env -p <project> logs -f app`, а `db` на EU-сервере нет совсем (Postgres — на РФ-сервере, логи
там — `journalctl -u postgresql`); см. `docs/DEPLOY_PROFILE_B.md` §4.

Логи — pino JSON в stdout, ротацию делает сам Docker (`max-size: 10m, max-file: 5`, SPEC §18) —
никакого `logrotate` настраивать не нужно. На уровне `info` и выше в логах нет текстов сообщений,
имён и username (redaction путей `*.text`, `*.caption`, `*.first_name`, `*.last_name`,
`*.username`, токенов и ключей — CLAUDE.md); в отчёте об ошибке ищите только ID сущностей
(`chatId`, `userId`, `proposalId` и т. п.), не пересылайте фрагменты лога с текстами наружу, если
вдруг такой текст там окажется (признак бага в redaction, а не нормальная находка).

Полезные выборки без `-f` (постранично, без слежения):

```bash
./scripts/compose.sh logs --since 1h app | grep -i error
./scripts/compose.sh logs --tail 200 app
```

## `/admin`

Личное сообщение боту `/admin` (только для `SUPERADMIN_TG_IDS` из `.env`, вне зависимости от
того, кто сейчас Owner workspace'а — D40 касается уведомлений, а не доступа к `/admin`). Панель
показывает (SPEC §18, `src/bot/views/admin.ts`):

- версию (git sha) и аптайм процесса;
- очередь необработанных предложений по чатам (`pendingByChat`) — чаты, где есть хотя бы одна
  `pending`-proposal, которую Owner ещё не разобрал;
- ИИ-блок: стоимость LLM за сегодня и за месяц, число proposals (показано/скрыто/принято/
  отклонено) за последние 7 дней и точность `accepted/(accepted+rejected)` (`н/д`, если
  знаменатель 0);
- **Последние ошибки** — до `RECENT_ERRORS_LIMIT` (`src/config/constants.ts`, по умолчанию 5)
  самых недавних различных ошибок (`src/domain/system/errorReports.ts`'s `listRecentErrors`),
  новые сверху; каждая — время, имя исключения и сообщение. Пусто («Ошибок не было») — не значит,
  что совсем ничего не происходило: сюда попадают только ошибки с сохранённым `sample` (реальные
  исключения, прошедшие через `src/ops/errorReporter.ts`), а не оповещения `errors.alert(...)`
  без примера (`ticker_gap`, `privacy_mode`, `cards:owner-blocked`, превышение дневного бюджета и
  т. п.) — те приходят отдельными сообщениями в личку, а не через эту панель.

Кнопки под панелью:

- **Код владельца** — выпускает одноразовый код передачи (`/transfer`'s логика без выбора
  demote/remove, см. `docs/MIGRATION_TO_OWNER.md` и SPEC §17.3, п. 3); можно выпустить и для
  пустого workspace (ещё нет Owner).
- кнопка настроек ИИ (`renderAdminAiSettingsButton`);
- **Удалить workspace полностью** — два подтверждения подряд (SPEC §19.3.3), безвозвратно удаляет
  workspace, чаты, сообщения, задачи, участников; использовать только по явному запросу
  руководителя/при полном сворачивании — не путать с точечным удалением данных одного участника
  (`/people → участник → Удалить данные`, см. раздел «Инциденты» ниже).

Скрытая superadmin-диагностика: `/testerror` всегда бросает исключение (проверка пайплайна отчётов
об ошибках, `src/bot/middleware/errors.ts`) — не отвечает не-суперадминам вовсе, чтобы не быть
обнаруживаемой.

## `/debug`

`/debug [chatId]` — личное сообщение, только для `SUPERADMIN_TG_IDS`, показывает до 10 последних
`analysis_batches` (по умолчанию по всем чатам, с аргументом — по одному чату; `chatId` — это
внутренний `chats.id`, который сам `/debug` и показывает, не «сырой» Telegram chat id). На каждый
батч: время, число сообщений, статус (`queued`/`running`/`done`/`failed`), сколько карточек
показано/скрыто и почему (`suppressedReasons`), модель и стоимость, текст ошибки (если была).

`/reanalyze <chatId> [lastN]` — тоже superadmin-only (не Owner-only, см. doc-комментарий в
`src/bot/handlers/admin.ts`) — ставит повторный анализ последних `lastN` сообщений чата (или всех
необработанных, если без `lastN`); использовать после правки промпта/модели или когда batch завис
в `failed`/`queued` — см. «Инциденты» ниже.

Оба — только в личке (DM-only): в группе отвечает лишь `/privacy` (SPEC §12.2).

## Диск

```bash
df -h               # свободное место на /
docker system df     # что занимает место внутри Docker (образы, volume, build cache)
```

Основной источник роста — каталог `backups/` (до 14 файлов на окружение, см. раздел «Бэкапы»
выше) и накопившиеся старые образы приложения после серии деплоев. Чистка:

```bash
docker image prune -f        # старые неиспользуемые образы (замещённые новыми тегами)
docker system prune -f       # агрессивнее: ещё и остановленные контейнеры, неиспользуемые сети
```

`docker system prune` не трогает именованные volume (в т. ч. volume БД) без флага `--volumes` —
не добавлять этот флаг на живом стеке.

## Обновление и откат

Деплой и откат конкретного тега — `scripts/deploy.sh` (подробное описание, ожидаемый вывод и
разбор ошибок — `docs/DEPLOY.md` §11; здесь не дублируется):

```bash
cd /opt/stb-prod
./scripts/deploy.sh v0.2.0    # деплой — делает pre-deploy backup, затем pull+up, затем /healthz
./scripts/deploy.sh v0.1.0    # откат — тот же скрипт с предыдущим тегом
```

`deploy.sh` откатывается и сам, автоматически, если новый тег не прошёл `/healthz` за 90 секунд
(`docs/DEPLOY.md` §11) — ручной откат обычно нужен только если нашли проблему уже после того, как
health-check прошёл (например, деградацию заметили не сразу). Текущий задеплоенный тег —
`cat .deploy/current_tag`.

## Типовые инциденты

### Превышен дневной бюджет LLM

Симптом: superadmin и Owner получают уведомление о превышении `LLM_DAILY_BUDGET_USD` (по
умолчанию 1.0, SPEC §16); автоанализ ставится на паузу, новые сообщения копятся как `pending`,
ручные команды (`/reanalyze` и т. п.) продолжают работать.

- Это ожидаемый аварийный тормоз, не авария сама по себе — анализ возобновится автоматически на
  следующие сутки **по часовому поясу workspace'а** (`src/scheduler/jobs/analyze.ts`: граница
  суток считается в `deps.workspace.timezone`, не в UTC — например, при `Europe/Moscow` новый
  дневной лимит открывается в 00:00 MSK, а не в 00:00 UTC).
- Если лимит систематически мал для реальной нагрузки — поднять `LLM_DAILY_BUDGET_USD` в `.env`
  обоих стеков и перезапустить: `./scripts/compose.sh up -d`.
- Проверить `/admin`: стоимость за сегодня/месяц — не превышает ли расход и общий лимит ключа
  OpenRouter (`docs/DEPLOY.md` §6 — spend limit на самом ключе — это отдельный, более жёсткий
  тормоз на случай бага).
- Накопившиеся `pending`-сообщения не теряются: они дождутся следующих суток или `/reanalyze`.

### Бот заблокирован пользователем (руководителем или сотрудником)

Симптом: отправка в личку возвращает `403 Forbidden: bot was blocked by the user`; планировщик
(`src/scheduler/jobs/notify.ts`, `cards.ts`) ставит `users.dm_blocked=true` этому пользователю и
отменяет все его запланированные напоминания (SPEC §13.1); карточки и сводки этому человеку не
доставляются.

- Попросить человека написать боту `/start` в личке хотя бы раз — Telegram не позволяет боту
  писать первым, только отвечать.
- **Известное ограничение:** сам факт, что человек снова открыл чат с ботом (`/start`), **не**
  сбрасывает `dm_blocked` автоматически — ни один код-путь сейчас не возвращает его в `false` (пробел
  фазы 3, найден и задокументирован при финальном ревью фазы 4, не исправлялся в её рамках).
  Сброс — ручной шаг: зайти в БД как superadmin и выполнить (`users.tg_user_id` — Telegram ID
  человека, не внутренний `users.id`):
  ```bash
  cd /opt/stb-prod   # или /opt/stb-dev
  ./scripts/compose.sh exec db psql -U stb -d stb \
    -c "UPDATE users SET dm_blocked = false WHERE tg_user_id = <TELEGRAM_ID>;"
  ```
  (`stb`/`stb` — `POSTGRES_USER`/`POSTGRES_DB` по умолчанию из `.env.example`; подставить реальные
  значения, если на этом сервере они другие.) Без этого шага карточки и напоминания этому человеку
  не возобновятся даже после повторного `/start`.
- Если это Owner — до восстановления DM карточки о новых задачах не доходят вовсе (критично,
  «пропуск задачи хуже ложного срабатывания» — проверять первым делом при жалобе «бот молчит»).

### Включён Privacy Mode в BotFather

Симптом: superadmin получает сообщение-предупреждение при старте приложения (проверка
`getMe`/`can_read_all_group_messages` — SPEC §18); бот физически не видит сообщений участников в
группах (видит только команды и сообщения, адресованные ему напрямую).

- В @BotFather: выбрать бота → `/setprivacy` → **Disable**.
- **Затем бот должен быть удалён и заново добавлен в каждую рабочую группу** — включение privacy
  mode не распространяется на уже существующее членство бота в группе (`docs/DEPLOY.md` §5,
  CLAUDE.md «Грабли»). Простого «подождать» или перезапуска стека недостаточно.
- После этого делать тестовое сообщение с поручением в одной из групп и убеждаться, что карточка
  дошла (как в `docs/DEPLOY.md` §9).

### OpenRouter недоступен

Симптом: подряд несколько ошибок LLM (5 подряд — порог для оповещения superadmin, SPEC §18);
`/debug` показывает батчи в статусе `failed` с текстом ошибки.

- Проверить сам OpenRouter: `curl -sS https://openrouter.ai/api/v1/models | head` (как в
  `docs/DEPLOY.md` §3) и статус провайдера (status-страница OpenRouter).
- Сообщения не теряются: батчи остаются в БД и дожидаются следующего прогона планировщика
  (SPEC §16's приёмка: «отключение OpenRouter не теряет сообщений»). Как только API снова
  отвечает, следующий тик анализирует накопившееся — специального действия обычно не требуется.
- Если нужно ускорить восстановление после сбоя (не ждать следующего тика) — `/reanalyze <chatId>`
  для конкретного чата.
- Если недоступность длительная и критична — переключение на другого провайдера через
  `LLM_PROVIDER` (SPEC §19.3, п. 6) — отдельная задача, не делается на лету без тестов.

### Миграция group → supergroup

Симптом: Telegram сам превращает обычную группу в supergroup (например, при включении истории
сообщений или добавлении более 200 участников) и присылает служебное обновление с
`migrate_to_chat_id`; старый `tg_chat_id` перестаёт получать сообщения.

- Приложение само обрабатывает `migrate_to_chat_id`, обновляя `chats.tg_chat_id` и `chats.type` на
  `supergroup` (SPEC, раздел про схему `chats`) — специального ручного действия обычно не требуется.
- Проверить тестовым сообщением с поручением, что карточка всё ещё доходит, и что ссылки на
  сообщения в карточках стали вида `https://t.me/c/<chat_id без -100>/<message_id>` (supergroup
  даёт прямые ссылки, обычная группа — только цитату без ссылки, SPEC, раздел про карточки).
- Если карточки перестали приходить именно после миграции — смотреть лог приложения на ошибки
  обработки обновления, прежде чем подозревать что-то другое.

### Ротация токена бота

Когда нужно: компрометация токена, плановая передача бота новому владельцу (см.
`docs/MIGRATION_TO_OWNER.md`, SPEC §17.3, п. 8), или просто подозрение, что токен утёк
(например, засветился в публичном репозитории — проверка `git diff --cached` перед коммитом,
CLAUDE.md, должна была это предотвратить, но если всё же случилось):

1. В @BotFather: выбрать бота → `/revoke` — старый токен немедленно перестаёт работать, выдаётся
   новый.
2. Обновить `.env` на сервере: `TELEGRAM_BOT_TOKEN=<новый токен>`.
3. Перезапустить стек тем же тегом, что уже задеплоен: `./scripts/compose.sh up -d` (не
   `deploy.sh` — это не смена версии образа, а смена конфигурации).
4. Проверить `/healthz` и отправить себе `/start` — убедиться, что бот отвечает под новым токеном.

Старый токен после `/revoke` нигде больше действовать не должен — если он случайно попал в
git-историю публичного репозитория, `/revoke` — единственное реальное противодействие (переписать
историю публичного репо после того, как её кто-то мог увидеть, не считается надёжной защитой).

### Ticker не работал N мин (оповещение при старте)

Симптом: superadmin получает в личку сообщение-предупреждение «⚠️ Ticker не работал N мин.
Планировщик был остановлен (сбой или деплой) — проверьте логи сервиса.» сразу после старта
приложения (`src/ops/watchdog.ts`'s `checkTickerGapOnStart`, SPEC §18).

Означает: цикл планировщика (тикер — напоминания, сводки, авто-анализ) не работал минимум N минут
(порог — 2 минуты, `TICKER_GAP_ALERT_MS`) непосредственно перед этим запуском приложения — проверка
сравнивает `app_state['ticker:heartbeat']` (время последнего тика до остановки) с текущим моментом
при старте, один раз, до первого нового тика.

- Это не обязательно поломка — обычный плановый деплой (`deploy.sh`/`compose.sh up -d`) тоже
  останавливает тикер на время перезапуска контейнера. Сопоставить время алерта с временем
  последнего деплоя/перезапуска (`./scripts/compose.sh logs --since 1h app`, время в
  `.deploy/current_tag`'а не хранится, но видно по времени самого деплоя в истории команд/CI) —
  если N примерно совпадает с ожидаемым временем простоя при обычном деплое, это штатно, никаких
  действий не требуется.
- Если N заметно больше обычного времени деплоя (например, сервер падал, контейнер был в
  `Restarting`, или деплой зависал) — посмотреть логи приложения вокруг этого интервала
  (`./scripts/compose.sh logs --since <время> app`) на причину простоя, прежде чем считать
  инцидент закрытым.
- Пропущенные за это время напоминания/авто-анализ не теряются навсегда: следующий тик (сразу
  после старта) подхватывает всё накопившееся (та же логика, что при недоступности OpenRouter
  выше) — специального восстановительного действия обычно не требуется, только диагностика причины
  простоя.
