# CLAUDE.md — school-task-bot («Секретарь школы»)

Правила для всех агентов. Справочник (ID Context7, проверенные факты о библиотеках, карта модулей, известные ловушки) лежит в `docs/agents/reference.md`: открывай его только когда он нужен.

- С пользователем общаемся на русском. Код, идентификаторы, комментарии, коммиты и ветки — на английском. Тексты бота — на русском, вежливо, на «вы», только в `src/bot/texts/ru.ts`.
- Проект: Telegram-бот руководителя школы. Он читает рабочие группы, с помощью LLM (OpenRouter) находит задачи, присылает руководителю карточки, ведёт задачи, напоминания и сводку. **Пропуск задачи хуже ложного срабатывания.**

## Источники правды

Приоритет: указание пользователя → `SPEC.md` (бизнес-правила, «SPEC §N») → `plan.md` (задачи и решения D1…Dn) → этот файл. Если план расходится со SPEC или SPEC неполна там, где нужно бизнес-решение, — остановись и спроси, правила не выдумывай. Решения D-таблицы в `plan.md` обязательны. Среди них пользовательские: **D12** (пауза и анализ чата), **D40** (уведомления получает только руководитель), **D43** (TDD и ревью только для критичных задач).

## Рабочий процесс

1. Фазы идут строго по порядку. Ветка на фазу — `phase-<N>-<slug>`. В `main` напрямую не пушим, force-push запрещён.
2. Задача: сверить API через Context7 → реализовать → `pnpm format` и затем `pnpm lint && pnpm typecheck && pnpm test` зелёные (CI проверяет и `format:check`) → отметить `- [x]` в `plan.md` → коммит (Conventional Commits) → `git push` в ветку фазы.
3. **TDD (тест первым) — только для задач из списка D43:** 1.7, 1.12; 2.1, 2.2, 2.5–2.10, 2.12, 2.13; 3.1–3.3, 3.12; 5.2, 5.3; проверка `initData` в фазе 6. Остальные задачи пишутся сразу. Тесты из плана для них необязательны; новые тесты пишем, только если они входят в приёмку фазы или правка затрагивает модуль из списка.
4. **Ревью:** задачи из списка D43 проверяются по одной (рискованные — на Opus). Остальные — группами по 2–3 задачи одним ревьюером. В конце фазы — общее ревью на Opus.
5. Конец фазы: `docs/` и `CHANGELOG.md`, PR в `main`, зелёный CI, отчёт пользователю. Мерж (`gh pr merge --merge`) — только после подтверждения пользователя.
6. Без явного разрешения пользователя не делаем: деплой, настройки GitHub, реальные вызовы LLM (eval), действия в реальных чатах, удаление данных.
7. Исполнение идёт через `stb-orchestrator` — по одной фазе. Субагенты вызываются только типами `stb-implementer` (`stb-implementer-light` со средним уровнем рассуждений — для задач вне списка D43) и `stb-reviewer` с явной моделью: по умолчанию Sonnet, Opus — для рискованных ревью, раундов исправлений 4–5 и финального ревью. Тип `general-purpose` не используем: он наследует дорогие настройки сессии. Оркестратор работает сегментами: после двух завершённых блоков ревью он пишет `HANDOFF` в журнал и завершается, а главная сессия запускает нового.
8. **Экономия контекста:** не читай `plan.md` и `SPEC.md` целиком. Бери выдержку задачи (`task-brief`), нужные строки D-таблицы (`grep '^| D40 '`) и нужный раздел SPEC.

## Правила кода

- TypeScript strict + `noUncheckedIndexedAccess`, ESM (импорты с `.js`), **без `any`**.
- Все внешние данные проходят через zod: env, LLM, HTTP, `callback_data`, jsonb. `z.coerce.boolean()` не использовать.
- Время: в БД только UTC. Часовые пояса — только luxon. В `domain/`, `ai/`, `scheduler/`, `time/` текущее время берётся только из `clock.now()`. `Date.now()`, `new Date()` без аргументов и SQL `now()` для бизнес-логики запрещены.
- Кириллица в `src/**/*.ts` допустима только в `src/bot/texts/ru.ts` и `src/config/constants.ts` (проверяет `tests/unit/architecture.test.ts`). Промпты лежат в `prompts/*.md`.
- `domain/`, `ai/`, `time/`, `scheduler/` не импортируют grammY. Отправка в Telegram — через интерфейс `Messenger` (`src/domain/messenger.ts`). `bot/views/` — чистые функции, возвращают `{ text, buttons }`.
- Telegram: `parse_mode: 'HTML'` и `escapeHtml` для пользовательского текста; сообщение ≤ 4096 символов; `callback_data` ≤ 64 байт, формат `v1:<entity>:<action>:<id>[:<arg>]` — только через `src/bot/keyboards/callbackCodec.ts`.
- Права проверяются по БД на каждом callback и команде (`src/domain/people/permissions.ts`). `callback_data` не доверяем.
- Идемпотентность: решения — через `UPDATE … WHERE status='pending' RETURNING`; уведомления — через уникальный `dedupe_key`; планировщик — `FOR UPDATE SKIP LOCKED`; карточки — через outbox (`proposals.notified_at`).
- Логи: pino, без текстов сообщений, имён и username на уровне `info` и выше. В отчётах об ошибках — только ID.
- LLM: температура 0, перед отправкой псевдонимизация (`src/ai/pseudonymize.ts`). Реальные вызовы LLM в тестах и CI запрещены, только fixtures.
- Зависимости — только из SPEC §4 плюс dev-инструменты `tsx`, `@vitest/coverage-v8`, `vite`, `@types/node`, `@types/luxon`, `eslint-config-prettier`. Для остальных нужен запрос пользователю.
